# NVK поверх GSP-RM: крейт `nvgpu`

Цель (18.11.2026): неизменённый Mesa NVK (`libvulkan_nouveau.so`, Debian
25.0.7) на RTX 3060. Ядро изображает uAPI DRM nouveau (`/dev/dri/renderD128`)
поверх своего GSP-RM. Полная спецификация — `nvk-spec.md` (вехи M0–M8, пакеты
WP-A..WP-D); ход работ — раздел «Видеокарта для игр: NVK поверх GSP-RM» в
`ROADMAP.md`.

`crates/nvgpu` — чистая логика без ядра (`no_std` + `alloc`), проверяется на
хосте: `cargo test -p nvgpu`. Собирается и для `x86_64/aarch64-unknown-none`.

| модуль | что | кто пользуется |
|--------|-----|----------------|
| `backend` | трейт `GpuBackend` (договор, раздел 3.5), `GpuInfo`, `Place`, ручки, `Push`, `Errno`, номера классов | все |
| `uapi` | структуры DRM/nouveau/NVIF, номера ioctl (сверяются при компиляции), `Ioctl::decode`, `Pod`, разбор NVIF и ответ SCLASS | WP-C |
| `arena` | `RangeAlloc` (куски, выравнивание, слияние), `VramAlloc` — служебная (BAR1) и общая арены из нескольких кусков | WP-A, SoftGpu |
| `gmmu` | PDE/PTE GP100+, kind, построитель таблиц над `PtMem`, разреженность, обход, блок экземпляра, регистры TLB | WP-A, SoftGpu |
| `gpfifo` | запись GPFIFO, заголовки методов, сегмент забора, учёт кольца, константы C56F/C7B5, `PushBuilder` | WP-A, SoftGpu, тесты |
| `syncobj` | двоичные/временные синхрообъекты (учёт), `wait_poll` с семантикой Linux, `HandleTable` | WP-C |
| `vaspace` | учёт VA файла: VM_INIT, разбор и атомарное исполнение VM_BIND по правилам `nouveau_uvmm.c` -> действия для бэкенда | WP-C |
| `softgpu` | `SoftGpu: GpuBackend` для QEMU и тестов, `SoftHost` (что даёт ядро), `HeapHost` (куча для тестов) | WP-C, WP-D |

## Что важно знать

- **PD0 — двойная запись 16 Б: таблица страниц 4 КиБ — во второй половине
  (`data[1]`, байты 8..15)**, первая — большие страницы. В спецификации 2.5
  было наоборот; сверено с `gp100_vmm_pd0_pde` и `vmm.c` (`pt[type == SPT]`).
- kind: 16 значений Turing+, 0x07 и 0x0f — `EINVAL`, сжатые 8..14 — заменяются
  несжатыми (сжатия нет).
- Таблицы, которые записал RM (диапазон «server reserved», 512 МиБ в начале
  области ядра), `Gmmu` не освобождает — помнит только свои.
- `SoftGpu` исполняет через настоящие таблицы страниц: хост-методы канала
  (SET_OBJECT, SEMAPHOREA..D, SEM_*), копировальный движок (линейно,
  многострочно, REMAP-заливка, семафоры, физические адреса), у 3D/compute/I2M —
  LOAD_INLINE_DATA и семафор отчёта. Шейдеры не исполняются. Обращение мимо
  отображения, неизвестный заголовок, метод без объекта, блочная раскладка,
  невыполнимый захват семафора — канал убит (`ENODEV`), причина —
  `SoftGpu::chan_killed`.
- Исполнение синхронное: `chan_submit` сразу прогоняет кольцо.
- Буфер должен жить, пока отображён (`VaSpace::bo_mapped`), — как у Linux, где
  отображение держит ссылку на GEM.
